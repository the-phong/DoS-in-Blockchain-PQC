## 3. Encoding, authentication and state

A V1 transaction is exactly `145 + N` bytes, with chain ID length `N` in 1–50: `PLUTOTX1 || uint16_be(1) || uint16_be(N) || chain_id || compressed_pubkey[33] || receiver[20] || uint64_be(amount) || uint64_be(nonce) || r[32] || s[32]`. Total size is 146–195 bytes. The signature covers the first `81 + N` bytes under `SHA-256("PLUTO/B0/SIGN/V1\0" || uint32_be(unsigned_length) || unsigned_bytes)`. Chain ID and every transfer field are signed. secp256k1 point and scalar validity, low-S and ECDSA verification are specified against SEC 1/SEC 2. The sender address is the first 20 bytes of `SHA-256("PLUTO/B0/ADDR/V1\0" || compressed_pubkey)`. TxID is a distinct domain-separated SHA-256 of full canonical wire bytes. Validation order and error precedence are explicit.

The proposed V2 logical state is version, chain ID, height, total supply and sorted `(address, balance, nonce)` accounts. Genesis allocation bytes have a separate `PLUTOG2!` magic, sorted unique positive allocations, checked supply and nonce zero. A successful distinct-address transfer debits/credits with checked arithmetic and increments only sender nonce; self-transfer increments nonce with net-zero balance; a failed transaction changes no account, nonce or supply. Zero-balance accounts remain to preserve nonce. Empty blocks increment height. The 32-byte V2 AppHash covers version, chain ID, height, supply and every sorted account; it is not a Merkle/Ethereum root. Phase 02 `PLUTO02!`/V1 records are retained; fresh B0 genesis is proposed, and no implicit or destructive migration exists.

## 4. ABCI safety policy

`CheckTx` is a committed-state admission filter; it can conservatively reject a future nonce. `PrepareProposal` selects valid candidates in supplied order with a throwaway state. `ProcessProposal` independently and deterministically simulates the complete proposal, including proposer-injected bytes never checked locally, and rejects invalid transactions or fixed block limits. `FinalizeBlock` re-evaluates the decided sequence, returns exactly one result per input transaction, applies valid transactions in order and skips invalid ones without state effect. An anomalous decided block over the fixed limits produces Code 10 for every transaction and no transaction state change; height still advances. Thus an invalid transaction is not confused with an ABCI transport error or reported as a success. Accepted proposals produce only successful final results under the same committed state. `Commit` alone makes pending state durable. Query is proposed as latest committed account data without proof. Snapshot/state sync and vote extensions remain unsupported.

Consensus-critical validity depends only on relevant committed state and the complete proposal. The proposed 6,144-tx/1,048,576-byte application limits are fixed and independently testable with canonical transactions; local clocks, CPU, queues or mempool arrival order cannot alter `ProcessProposal`, final results or AppHash. Physical atomic storage and crash recovery remain Phase 03C design/test work.

## 6. Risks and review questions

- **Protocol review required:** The owner/controller must accept or revise fee-free units and human display scale; address length/derivation; 65,536-account and block limits; and whether any Phase 02-to-V2 migration should ever be specified. Proposed rules are exact but not accepted.
- **ABCI policy review required:** The deterministic invalid-decided-block fallback, strict `ProcessProposal` rejection and latest-only query need approval against the pinned v0.38.26 contract and four-validator liveness expectations.
- **Cryptographic evidence missing by design:** Phase 03B must select/pin a library, generate exact bytes from explicitly nonproduction scalars, independently verify signatures/digests/addresses, and record positive and negative vectors. No library is imported now.
- **State implementation risk:** V2 flat commitment may become costly; physical storage, atomic commit, fault injection, replay and any migration need separate Phase 03C design. No crash-safety or multi-validator claim follows from this document.
- **Operational baseline limits:** Phase 02's localhost configuration trust boundary and absent branch protection were documented in Phase 02R. This phase does not alter either.
