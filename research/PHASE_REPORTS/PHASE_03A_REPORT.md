## 3. Encoding, authentication and state

A V1 transaction is exactly `145 + N` bytes, with chain ID length `N` in 1–50: `PLUTOTX1 || uint16_be(1) || uint16_be(N) || chain_id || compressed_pubkey[33] || receiver[20] || uint64_be(amount) || uint64_be(nonce) || r[32] || s[32]`. Total size is 146–195 bytes. The signature covers the first `81 + N` bytes under `SHA-256("PLUTO/B0/SIGN/V1\0" || uint32_be(unsigned_length) || unsigned_bytes)`. Chain ID and every transfer field are signed. secp256k1 point and scalar validity, low-S and ECDSA verification are specified against SEC 1/SEC 2. The sender address is the first 20 bytes of `SHA-256("PLUTO/B0/ADDR/V1\0" || compressed_pubkey)`. TxID is a distinct domain-separated SHA-256 of wire bytes that pass exact structural and low-S scalar eligibility, independent of later key, signature or state validity. Validation order and error precedence are explicit.

The accepted V2 logical state is version, chain ID, height, total supply and sorted `(address, balance, nonce)` accounts. Genesis allocation bytes have a separate `PLUTOG2!` magic, sorted unique positive allocations, checked supply and nonce zero. A successful distinct-address transfer debits/credits with checked arithmetic and increments only sender nonce; self-transfer increments nonce with net-zero balance; a failed transaction changes no account, nonce or supply. Zero-balance accounts remain to preserve nonce. Empty blocks increment height. The 32-byte V2 AppHash covers version, chain ID, height, supply and every sorted account; it is not a Merkle/Ethereum root. Phase 02 `PLUTO02!`/V1 records are retained; accepted B0 V1 requires fresh genesis, and no implicit or destructive migration exists.

## 4. ABCI safety policy

`CheckTx` is a committed-state admission filter; it can conservatively reject a future nonce. `PrepareProposal` selects valid candidates in supplied order with a throwaway state. `ProcessProposal` independently and deterministically simulates the complete proposal, including proposer-injected bytes never checked locally, and rejects invalid transactions or fixed block limits. `FinalizeBlock` re-evaluates the decided sequence, returns exactly one result per input transaction, applies valid transactions in order and skips invalid ones without state effect. An anomalous decided block over the fixed limits produces Code 10 for every transaction and no transaction state change; height still advances. Thus an invalid transaction is not confused with an ABCI transport error or reported as a success. Accepted proposals produce only successful final results under the same committed state. `Commit` alone makes pending state durable. Query is specified as latest committed account data without proof. Snapshot/state sync and vote extensions remain unsupported.

Consensus-critical validity depends only on relevant committed state and the complete proposal. The accepted 6,144-tx/1,048,576-byte application limits are fixed and independently testable with canonical transactions; local clocks, CPU, queues or mempool arrival order cannot alter `ProcessProposal`, final results or AppHash. Physical atomic storage and crash recovery remain Phase 03C design/test work.

## 6. Accepted rules and remaining implementation risks

- **Accepted protocol:** The Owner accepted fee-free indivisible units, 20-byte address derivation, 65,536-account and block limits, fresh B0 genesis, deterministic invalid-decided-block fallback, strict `ProcessProposal` rejection and latest-only query. A human display scale is an implementation/UI choice that cannot alter wire units. Changing any accepted rule requires a new decision.
- **ABCI implementation risk:** The accepted fallback, proposal rule, block limits and query still need implementation tests against pinned v0.38.26 and four-validator liveness. Owner acceptance is not runtime evidence.
- **Cryptographic evidence missing by design:** Phase 03B must select/pin a library, generate exact bytes from explicitly nonproduction scalars, independently verify signatures/digests/addresses, and record positive and negative vectors. No library is imported now.
- **State implementation risk:** V2 flat commitment may become costly; physical storage, atomic commit, fault injection, replay and any migration need separate Phase 03C design. No crash-safety or multi-validator claim follows from this document.
- **Operational baseline limits:** Phase 02's localhost configuration trust boundary and absent branch protection were documented in Phase 02R. This phase does not alter either.

## 8. Controller rework of the same Phase 03A proposal

The Controller reviewed commit `c6a719aff70b1fd03027b643005732337667128c` on existing Draft PR #3 and returned **REWORK**. The same branch and PR were retained. D-020–D-022 were **Proposed at that time** and were subsequently accepted by the Owner after the corrected commit `e205a2195d3beb634842cf986e1df5d0ed542dbb`.

- **R1 — Validation cost and precedence:** The common evaluator now checks structure, chain match, positive amount and fixed-width scalar range/low-S before point decompression and ECDSA. The exact first-failure order and Code 1/2/5/4/3/4/6/7/8/9/0 mapping are shared by admission, proposal and final execution. A zero-amount record is Code 5 even if its canonical signature subsequently would not verify. This reduces unnecessary cryptographic work for cheap invalid inputs without adding an admission optimization. Future invalid-workload studies must label rejection stage and compare matched B0/B1 workloads; an invalid zero-amount workload no longer measures ECDSA verification cost. Structural, state-independent cryptographic and state-dependent checks are explicitly classified in transaction V1.
- **R2 — Nonce boundary:** Every success requires candidate sender nonce `< MaxUint64`; a matching wire/current `MaxUint64` returns Code 6 `invalid_nonce` before balance, overflow or cap checks and changes no state. V17 and new V25 exercise the rule and its precedence.
- **R3 — TxID eligibility:** The independent byte predicate is exact structural V1 format and canonical scalar range/low-S only. Malformed wire or noncanonical scalars have no Pluto TxID. A 33-byte invalid point/prefix, canonical-scalar but nonverifying signature, wrong chain, or nonce/balance failure can have one. Invalid amount can also have one. Error precedence does not determine TxID existence; the predicate does. The vector plan states the outcome for every case.
- **R4 — RPC identity:** Pinned CometBFT v0.38.26 computes `types.Tx(wire).Hash()` as `SHA-256(wire)`; Pluto TxID includes its own domain and length prefix. Future tests record both hashes and exact raw bytes, use CometHash for RPC lookup and block height/index to distinguish duplicate occurrences. Rejected admission may have no indexed block record. No RPC code was added.
- **R5 — Boundary fixtures and AppHash cost:** V20 now fixes chain IDs of length 1 and 50; 6,145 × 146 = 897,170 bytes with funded A balance 6,145 and sequential nonces 0..6,144; and 5,378 × 195 = 1,048,710 bytes with funded A balance 5,378 and sequential nonces 0..5,377. All transactions must be individually signed with valid low-S ECDSA and remain valid under sequential simulation if the envelope limit alone is ignored. Exact bytes/signatures are not yet generated. Full-state AppHash V2 recomputation is proportional to account count; B0/B1 studies must control account count and execution model.
